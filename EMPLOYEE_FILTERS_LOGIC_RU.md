# Логика фильтров сотрудников простыми словами

Этот файл объясняет не по строкам, а по смыслу: как вся цепочка работает целиком.
Представь, что у нас есть коробка с карточками сотрудников, и мы хотим быстро находить только нужных людей.

## Главная идея

Раньше список сотрудников можно было просто показать целиком.
Теперь список можно просеивать через "сито":
- по отделу;
- по минимальной зарплате;
- по максимальной зарплате;
- по минимальному возрасту;
- по максимальному возрасту.

То есть мы как будто говорим приложению:
"Покажи мне не всех подряд, а только тех, кто подходит под мои правила".

## Как идет сигнал от пользователя до сервера

### Шаг 1. Пользователь меняет фильтр

На экране есть форма фильтров.
Например, человек выбирает:
- отдел `QA`;
- зарплату от `10000` до `20000`;
- возраст от `25` до `40`.

Эти значения сохраняются в общем хранилище `zustand`.
Это как общая коробочка памяти, куда страница может заглянуть в любой момент.

### Шаг 2. `HomePage` читает фильтры

Файл `src/components/pages/HomePage.tsx` делает две важные вещи:
- берет текущие значения фильтров из стора;
- передает их в `useEmployees(...)`.

Значит, `HomePage` не фильтрует сотрудников сама.
Она просто говорит:
"Вот текущие правила. Пожалуйста, получи мне сотрудников по этим правилам".

### Шаг 3. `useEmployees` следит за изменениями

Файл `src/services/hooks/useEmployees.ts` работает как умный помощник.

Он делает так:
1. Получает полный объект фильтров из `HomePage`.
2. Сравнивает его с дефолтными значениями.
3. Оставляет только реально измененные поля.
4. Если изменений нет, превращает фильтры в `undefined`.
5. Кладет результат в `queryKey`.
6. Запускает `apiClient.getEmployees(activeFilters)`.

Почему важен `queryKey`:
если фильтры поменялись, React Query понимает, что это уже другой запрос.
Значит, нужно заново сходить за данными.

Пример:
- было `["employees", { department: "QA" }]`;
- стало `["employees", { department: "DevOps" }]`.

Для React Query это уже не одно и то же.
Поэтому она обновляет список.

### Почему это важно для фразы "если нужны все сотрудники"

Раньше была тонкая проблема.

Даже когда на экране стояли значения по умолчанию:
- отдел `Departments`;
- минимальная зарплата `5000`;
- максимальная зарплата `50000`;
- минимальный возраст `20`;
- максимальный возраст `75`;

приложение все равно считало, что фильтры есть.
Из-за этого на сервер уходил запрос не просто `GET /employees`, а запрос с параметрами диапазона.

То есть формально список был "почти все сотрудники", но требование задания выполнялось не строго.

Теперь это исправлено:
- если значения равны дефолтным;
- они выбрасываются из `activeFilters`;
- если после этого ничего не осталось, в `apiClient` уходит `undefined`.

А это уже означает:
- никаких query-параметров;
- обычный запрос `GET /employees`;
- сервер возвращает всех сотрудников без фильтрации.

### Шаг 4. `ApiClientJsonServer` переводит человеческие фильтры в язык сервера

Файл `src/services/ApiClientImpl.ts` получает понятные нам поля:
- `department`;
- `minSalary`;
- `maxSalary`;
- `minAge`;
- `maxAge`.

Но теперь туда попадают не все поля подряд, а только активные фильтры.
То есть если пользователь ничего реально не менял, этот шаг вообще получает `undefined`.

Если активные фильтры есть, сервер не понимает такие "человеческие" названия полностью.
Ему нужны специальные параметры.

Поэтому код делает перевод:
- `department` остается `department`;
- `minSalary` превращается в `salary_gte`;
- `maxSalary` превращается в `salary_lte`;
- `minAge` превращается в ограничение по дате рождения;
- `maxAge` тоже превращается в ограничение по дате рождения.

## Почему возраст переводится в дату рождения

Сервер хранит не возраст, а дату рождения.
Например, сервер знает:
- человек родился `1995-04-10`;
- человек родился `1988-11-03`.

Но пользователь спрашивает возраст:
- не младше `25`;
- не старше `40`.

Значит, возраст надо превратить в даты.

### Пример с минимальным возрастом

Если нужен возраст минимум `25`, значит сотрудник должен быть достаточно взрослым.
То есть он должен родиться не позже определенной даты.

Поэтому код делает:
- `minAge` -> `birthDate_lte`.

`lte` означает `less than or equal`, то есть "меньше или равно".
Для даты это значит:
"дата рождения раньше или равна границе".

Если человек родился раньше, он старше.
Это нам и нужно.

### Пример с максимальным возрастом

Если нужен возраст максимум `40`, значит сотрудник не должен быть слишком старым.
То есть он должен родиться не раньше определенной даты.

Поэтому код делает:
- `maxAge` -> `birthDate_gte`.

`gte` означает `greater than or equal`, то есть "больше или равно".
Для даты это значит:
"дата рождения позже или равна границе".

Если человек родился позже, он моложе.
Это нам и нужно.

## Что делает `getIsoDateFromAge`

Файл `src/utils/date_functions.ts` содержит помощника `getIsoDateFromAge(age)`.

Он работает так:
1. Берет сегодняшнюю дату.
2. Отнимает от текущего года возраст.
3. Ставит январь и первое число месяца.
4. Возвращает строку вида `YYYY-MM-DD`.

Пример:
- если сейчас `2026` год;
- и возраст `30`;
- функция вернет дату около `1996-01-01`.

Это не "магическая истина", а удобная граница для фильтрации.

## Как сервер отвечает обратно

После сборки параметров `ApiClientJsonServer` отправляет запрос на:
`GET /employees`

Если активные фильтры есть, к запросу добавляются параметры.
Примерно так:

```text
/employees?department=QA&salary_gte=10000&salary_lte=20000
```

Или с возрастом:

```text
/employees?birthDate_lte=2001-01-01&birthDate_gte=1986-01-01
```

Сервер возвращает только тех сотрудников, которые подходят под условия.

Если активных фильтров нет, запрос выглядит просто так:

```text
/employees
```

И это уже строго соответствует условию задания:
"если нужны все сотрудники, фильтры не используются".

## Зачем потом исправляется дата рождения

После ответа сервера код делает еще один важный шаг.
Он смотрит, как именно называется поле даты рождения:
- `birthDate`;
- `birthdate`;
- `dateOfBirth`.

Почему это нужно:
иногда сервер или старые данные называют одно и то же поле по-разному.
Из-за этого интерфейс может не увидеть дату и начать ошибаться.

Поэтому код делает простую подстраховку:
- находит реальную дату;
- записывает ее сразу в `birthDate`;
- и еще дублирует в `birthdate`.

Это как наклеить на одну коробку сразу две понятные надписи, чтобы любой работник склада быстро понял, что внутри.

## Что делает `getAge`

`getAge(birthDate)` считает возраст аккуратно.

Он:
1. Проверяет, что дата вообще есть.
2. Проверяет, что дата не сломана.
3. Считает разницу в годах.
4. Проверяет, был ли уже день рождения в этом году.
5. Если еще не был, уменьшает возраст на `1`.

Это нужно, потому что просто вычесть годы недостаточно.
Если человек родился в декабре, а сейчас март, то его день рождения еще не наступил.

## Что в итоге видит пользователь

Вся цепочка работает так:
1. Пользователь меняет фильтр.
2. Значение попадает в zustand-store.
3. `HomePage` читает новые значения.
4. `useEmployees` видит новые фильтры.
5. React Query запускает новый запрос.
6. `ApiClientJsonServer` превращает фильтры в параметры для сервера.
7. Сервер отдает подходящих сотрудников.
8. Интерфейс показывает уже отфильтрованный список.

## Что именно было исправлено

Исправление состоит в одном главном правиле:
- дефолтные значения больше не считаются настоящими фильтрами.

Теперь приложение сначала спрашивает:
"Пользователь правда что-то изменил или на экране все еще обычные стартовые значения?"

Если ничего не изменилось, то:
- фильтры убираются;
- запрос идет без `params`;
- сервер возвращает полный список сотрудников.

## Самое короткое объяснение

Эта логика делает вот что:
- берет желания пользователя из формы;
- превращает их в понятный серверу запрос;
- получает подходящих сотрудников;
- показывает их на странице.
